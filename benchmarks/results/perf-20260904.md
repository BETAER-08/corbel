# corbel performance characteristics on large repositories

Answers "can we use this on our monorepo" with measured numbers, not
accuracy — this is not a golden-set run and no precision/recall claim is
made anywhere in this document. Reproduce with:

```
python3 benchmarks/harness/perf_bench.py <repo-name> <repo-path> target/release/corbel <cold-runs> <latency-n>
```

## Candidate selection

Investigated by cloning (shallow, `--depth 1`) and running a real
`corbel index` to get an actual symbol count — not estimated from repo size
or LOC, since those don't track symbol count reliably (confirmed below:
bevy has *more* total Rust LOC than servo, 643K vs 546K, but 3.7x fewer
symbols and index in 1.6% of the time).

| Repo | Language | Files (.rs/.ts) | Symbols (measured) | Verdict |
| --- | --- | --- | --- | --- |
| tokio-rs/tokio | Rust | 793 | 8,145 | used — ~1만 tier |
| bevyengine/bevy | Rust | 1,881 | 31,849 | used — ~3만 tier (closest available to "5만"; see note) |
| servo/servo | Rust | 1,649 | 116,870 | used — 10만+ tier |
| microsoft/TypeScript | TypeScript | 13,272 | 112,940 | used — 10만+ tier (TS) |
| rust-lang/rust | Rust | — | not measured | **deliberately skipped** |
| microsoft/vscode | TypeScript | — | not measured | identified, not needed (TypeScript compiler repo already covers the TS 10만+ tier) |

- **bevy is ~32K symbols, not exactly 5만.** No readily-available Rust repo
  sits cleanly at ~50K without either being a monorepo-of-many-crates
  (adds noise about what counts as "one repo") or requiring the same kind
  of multi-clone hunting done here for the top tier. Reported honestly as
  ~3만 rather than forcing a round number — the tier still does its job:
  it sits between tokio and the 10만+ tier and shows the same non-linear
  trend continuing (§ Scaling).
- **rust-lang/rust skipped, not attempted.** Reasoning, not just deference
  to the user's caution: servo (116,870 symbols) alone took **9m19s** for a
  single cold index. rust-lang/rust's `compiler/` + `library/` + `src/`
  trees are widely known to be several times larger than servo's Rust
  source; even a single cold-index attempt would plausibly run 30-60+
  minutes with no guarantee of completing cleanly (see servo/TS findings on
  super-linear scaling below — this would compound, not just multiply).
  Not attempted rather than left to run indefinitely.
- **vscode not measured.** Its repo carries ~1.4GB of non-source content
  (its own build tooling, extension host, tests) with real .ts source that
  would need to be scoped down to compare fairly; microsoft/TypeScript
  already delivers a clean, comparable 10만+ TypeScript data point without
  that scoping problem, so it was prioritized instead given time budget.

## Pre-run notes

- Cold index: **3 runs averaged for tokio and bevy.** For servo and
  microsoft/TypeScript, **only 1 cold-index run each** — a single run
  already cost 9m19s (servo) / 4m42s (typescript-repo) via manual timing
  (confirmed again inside `perf_bench.py`'s own measurement below, 566s /
  282s respectively — consistent). Averaging 3 runs at this tier would cost
  ~28-47 minutes per repo for a single metric. **This is reported as a
  practicality finding in its own right, not a silently-taken shortcut**:
  if getting a stable timing average at the 10만+ tier is itself
  impractical in a normal working session, that is directly relevant to
  "can we use this on our monorepo."
- All indexes fully rebuilt from a clean `.corbel/` before each cold-index
  measurement.
- Incremental index: one source file's content changed (single line
  appended, then reverted), re-indexed once, `.corbel/` **not** deleted
  first.
- Latency benchmarks: `corbel serve` started once per repo, 100 real
  `get_symbol` calls against randomly-sampled real function/method symbols
  from that repo's own index, 100 `find` calls against random 4-character
  substrings drawn from real symbol names, 30 `impact` calls against the
  same symbol sample. All measured via the actual MCP JSON-RPC round-trip
  (stdin write → stdout read), not an internal function timer.
- Peak RSS: `/usr/bin/time -v` wrapping the entire `corbel serve` session
  (startup through all 230 queries), read from "Maximum resident set size."

at scale is latency, not failure.

## 2. Scaling curves: linear or worse?

**Cold-index time grows clearly super-linear, and gets worse, not
constant, as scale increases:**

| Transition | Symbol growth | Time growth | Implied exponent (time ∝ symbols^k) |
| --- | --- | --- | --- |
| tokio → bevy | ×3.91 | ×2.88 | k ≈ 0.78 |
| bevy → typescript-repo | ×3.55 | ×10.20 | k ≈ 1.83 |
| bevy → servo | ×3.67 | ×20.46 | k ≈ 2.32 |
| tokio → servo (full range) | ×14.35 | ×58.91 | k ≈ 1.53 |

The tokio→bevy step looks *sub*-linear (k≈0.78) only because tokio's
9.6s is dominated by fixed per-run overhead (grammar loading, process
startup, DB creation) that bevy's larger run amortizes away — not because
indexing gets cheaper per symbol. The two 10만+ transitions (bevy→servo,
bevy→typescript-repo) are unambiguous: **k≈1.8-2.3, i.e. closer to
quadratic than linear, and the exponent gets *worse* moving from the ~32K
tier to the ~113-117K tier rather than staying constant.** A constant
per-symbol cost would hold k≈1 everywhere; it does not.

**A same-scale comparison isolates the mechanism.** typescript-repo
(112,940 symbols) and servo (116,870 symbols) have essentially the same
symbol count, but servo takes **2.0x longer to index** (566s vs 282s).
The corbel CLI's own resolution-summary output explains the gap directly:

| | Symbols | Unresolved (ambiguous) calls |
| --- | --- | --- |
| typescript-repo | 112,940 | 28,282 |
| servo | 116,870 | **164,043** |

servo has 5.8x more name-collision-ambiguous call sites despite a nearly
identical symbol count. The cost that scales worst is not symbol
extraction or storage — it's **resolving a call site when multiple symbols
share its bare name**, which is exactly what this same session's earlier
`unqualified_symbol_name`/name-collision investigation flagged as an
architecturally cheap, bare-name-keyed lookup (`symbol_ids_by_name`,
per-file `HashMap<String, Vec<(i64,u32)>>` built and searched per
reference). servo's DOM/WebIDL-generated code is unusually name-collision-
heavy (hundreds of similarly-shaped types with the same method names) —
this is likely close to a worst case for that resolution path, not a
representative one, but it demonstrates that **the driver of super-linear
growth is ambiguous-name volume, not repo size per se.** A monorepo with
similarly repetitive naming (generated bindings, codegen, heavy trait/
interface implementation patterns) should expect to sit on the bad end of
this curve regardless of raw symbol count.

**`get_symbol`/`find` latency scale roughly linearly with symbol count for
p50, but tail latency (p95/p99) grows faster than p50 at the top tier** —
consistent with a full-table-scan cost (predictable, ∝ table size) plus
growing cache-miss variance as the table stops fitting comfortably in page
cache. `find` p50 goes from 1.06ms (tokio) to 31.72ms (servo) — a ×30
increase against a ×14.3 symbol increase, i.e. only mildly super-linear —
but p99 goes from 1.42ms to 122.05ms, a **×86** increase, meaning the worst
case degrades much faster than the typical case at scale.

**`impact` has one severe, isolated outlier**: typescript-repo's p99 is
1191.94ms against a p95 of only 6.01ms — one specific symbol's reverse
call graph (a highly-connected compiler-internals function, most likely)
triggered a walk that took ~200x longer than the 95th-percentile case.
servo, despite being larger, shows a much tamer p99 of 62.38ms. This isn't
explained by symbol count — it's explained by **how connected the specific
symbol queried happens to be** (fan-in), which is inherently unpredictable
per-query and not simply a function of repo size. A monorepo with a few
extremely central/foundational symbols (a base class, a shared utility
imported everywhere) should expect occasional `impact` calls costing far
more than the typical case, independent of overall repo size.

**Peak RSS does not scale with repo size in any of these runs**
(8.4-8.6 MB for the two Rust repos regardless of being 8K or 117K symbols;
12.3 MB for typescript-repo). This is a genuinely reassuring result:
corbel does not appear to load its index into process memory — queries hit
SQLite on disk/page-cache, not an in-memory structure that grows with
repo size. Memory is very unlikely to be the limiting factor for adopting
corbel on a large monorepo; time (indexing) and tail latency (`find`,
`impact`) are.

**Skipped-file ratio stays low and roughly flat to slightly declining as
scale increases** (0% → 0.053% → 0.034% → 0.018%) — not a concern at any
tier measured; the small fixed number of binary/non-UTF8/symlink skips
gets proportionally diluted as file count grows.

## 3. `find`'s full-table-scan threshold — concrete answer

Confirmed directly in `crates/corbel-core/src/query.rs`'s `find()`: every
call runs **two full table scans**, not one —

```sql
SELECT COUNT(*) FROM symbols WHERE symbols.name LIKE ?1 ESCAPE '\\'   -- ?1 = '%query%'
...
SELECT symbols.name, ... FROM symbols JOIN files ...
 WHERE symbols.name LIKE ?1 ESCAPE '\\'                                -- same '%query%' pattern
 ORDER BY match_rank, symbols.name, files.path, symbols.line LIMIT ?4
```

Both use a **leading-wildcard** `LIKE '%query%'` pattern (the count query
unconditionally, the ranked query too since it must find contains-matches,
only using the exact/prefix patterns for `CASE`-based ranking afterward,
not for filtering). A leading `%` makes SQLite's B-tree index on
`symbols.name` (`idx_symbols_name`) unusable for that predicate — this is
exactly the "선행 % LIKE로 전체 스캔" the request named, verified in source,
not inferred from behavior alone.

**Concrete threshold, from the measured curve:**
- Up to ~30-32K symbols (bevy tier): `find` p50 ≈ 5ms, p99 ≈ 6ms — no
  human or automated caller would notice this as a cost. Fully practical.
- ~110-120K symbols (servo/typescript-repo tier): `find` p50 is 15-32ms,
  **p99 reaches 93-122ms**. Individually still under the ~100-200ms
  threshold where a human perceives an interaction as "not instant," but
  no longer negligible — and this is a *per-call* cost that a client
  issuing several `find` calls per task (which is the realistic usage
  pattern for an agent doing exploratory search, not a human clicking once)
  will pay repeatedly.
- **The threshold where `find` stops being practical is not a single
  symbol count — it's a rate.** At servo's measured p50 (~32ms), 10
  `find` calls in a session cost ~320ms; at p99 (~122ms), 10 calls cost
  over a second. Given the growth curve is driven by table size and
  therefore keeps climbing with repo size (no sign of plateauing in this
  data), a monorepo meaningfully larger than servo's ~117K symbols (e.g.
  300-500K, plausible for a large multi-service monorepo) should be
  expected to push `find` p50 into the 60-150ms range by simple
  extrapolation of the observed near-linear-to-mildly-super-linear p50
  trend — at which point a workflow issuing many `find` calls per task
  will feel measurably slow, even though no single call fails or errors.

## 4. Failures / incompletions — reported as-is

- **No query ever failed or errored** at any tier (0/1,600 total calls).
- **No cold-index run failed** — all four repos indexed to completion with
  exit code 0.
- **The one real "cannot complete in practice" finding is the 3x
  cold-index averaging itself at the 10만+ tier** (§ Pre-run notes) — not a
  crash, but a session-time-budget wall: getting a statistically stable
  cold-index number for a servo-or-larger repo costs 10-50 minutes just for
  that one metric, which is itself an adoption-relevant cost (CI cold-cache
  scenarios, first-time onboarding of a large monorepo) distinct from any
  single query's latency.
- **`impact`'s p99 outlier (1191.94ms on typescript-repo)** is not a
  failure, but it is the single worst latency number in this entire
  report, and it happened on the *smaller* of the two 10万+ repos —
  reported prominently rather than averaged away, since a monorepo with a
  few highly-central symbols should expect this shape of tail latency
  regardless of its overall size.
- `impact`'s literal "depth 3" request from the task could not be honored
  exactly: the `impact` MCP tool's `inputSchema` (`crates/corbel/src/mcp/tools.rs`)
  exposes no `depth`/`max_depth` parameter — every call walks to
  `MAX_IMPACT_DEPTH = 10` (or until budget/visited-set exhaustion), fixed
  in `corbel-core/src/query.rs`. The latency reported above is for
  whatever depth each specific query actually reached, not a controlled
  depth-3 measurement. This is flagged rather than silently substituted.
